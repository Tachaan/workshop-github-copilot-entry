# GitHub Copilot のモードと機能の使い分け

GitHub Copilot には、質問、計画、実装、レビューなど、作業の段階に応じたモードや機能があります。まず **Ask で理解し、Plan で方針を決め、Agent で変更し、Code Review で確認する** と覚えると使い分けやすくなります。

| モード・機能 | 主な役割 | 成果物の例 |
| --- | --- | --- |
| Ask Mode | コードや問題を理解する | 説明、調査結果 |
| Plan Mode | 実装方針と影響範囲を整理する | 実装計画 |
| Agent Mode | 決まった方針に沿って変更する | コード、テスト、文書の変更 |
| GitHub Copilot Code Review | 変更後の抜け漏れを探す | レビュー指摘 |
| GitHub Copilot CLI | ターミナル上で支援を受ける | コマンドの説明や提案 |
| GitHub Copilot Cloud Agent | Issue をもとに非同期で作業する | Pull Request の変更案 |
| custom instructions / Agent Skills | チーム固有のルールや手順を伝える | 指示に沿った回答や変更 |

## Ask Mode

Ask Mode は、既存コードを変更せずに理解したいときに使います。既存コードの役割や処理の流れ、対象箇所の特定、エラーの原因調査に向いています。

### 使う場面

- 初めて読むコードの構造を知りたい
- 機能に関係するファイルを特定したい
- エラーの原因候補と確認方法を知りたい

### 頼み方の例

> Support Ticket Dashboard で、チケットのステータスを表示している箇所を特定してください。関連するファイルと、データが画面に届くまでの流れも説明してください。コードは変更しないでください。

### 注意点

- 回答は、実際のコードと照らし合わせて確認します。
- 原因調査では、エラーメッセージ、再現手順、期待する動作を伝えます。
- すぐに修正を依頼せず、まず事実と推測を分けてもらうと調査しやすくなります。

## Plan Mode

Plan Mode は、実装を始める前に方針を整理するときに使います。要件を作業単位に分け、変更するファイル、既存機能への影響、必要なテストを確認するのに向いています。

### 使う場面

- 複数ファイルに関わる変更の進め方を決めたい
- 実装方法を比較してから選びたい
- 変更範囲やリスク、テスト方針を確認したい

### 頼み方の例

> Support Ticket Dashboard に優先度フィルターを追加する計画を作成してください。変更が必要なファイル、各変更の目的、既存のステータスフィルターへの影響、必要なテストを挙げてください。まだファイルは変更しないでください。

### 注意点

- 計画に、要件にない機能や不要なリファクタリングが含まれていないか確認します。
- 不明な仕様を推測で確定せず、確認事項として分けてもらいます。
- 実装前に、人間が変更範囲と受け入れ条件を承認します。

## Agent Mode

Agent Mode は、方針が決まった修正を実際に進めるときに使います。複数ファイルのコード修正、テストの追加と実行、決まった内容のドキュメント更新などに向いています。

### 使う場面

- 承認済みの計画に沿ってコードとテストを変更したい
- 原因と修正方法が分かっている不具合を直したい
- 決まった仕様をドキュメントへ反映したい

### 頼み方の例

> 承認した計画に沿って、Support Ticket Dashboard に優先度フィルターを追加してください。既存の実装パターンを使い、関係するファイルだけを変更してください。必要なテストを追加して実行し、最後に変更ファイルとテスト結果を報告してください。

### 注意点

- 対象範囲、変更してはいけない箇所、完了条件を明示します。
- Agent が実行したコマンド、変更差分、テスト結果を確認します。
- 大きな変更は一度に任せず、確認可能な単位に分けます。
- 変更後は必ず人間がレビューします。

## GitHub Copilot Code Review

GitHub Copilot Code Review は、コードを変更した後に、差分の抜け漏れや問題の候補を確認する機能です。Ask、Plan、Agent の代わりではなく、実装後の確認として使います。

### 使う場面

- Pull Request の要件漏れや不具合を確認したい
- 既存機能への影響やテスト不足を探したい
- セキュリティや保守性の問題の候補を知りたい

### 頼み方の例

> Support Ticket Dashboard の優先度フィルター追加の差分をレビューしてください。未選択時の動作、絞り込み結果が 0 件の場合、既存のステータスフィルターとの併用、テスト不足を重点的に確認してください。

### 注意点

- 指摘には誤検知や見落としがあり得ます。
- 指摘を機械的に反映せず、要件とコードを確認して対応を判断します。
- Code Review を通しただけで、テストや人間のレビューを省略してはいけません。

## GitHub Copilot CLI（発展）

GitHub Copilot CLI は、ターミナルでコマンドや開発作業について支援を受けるための機能です。コマンドの意味を確認したり、目的に合うコマンドを提案してもらったりできます。

### 使う場面

- 不慣れなコマンドの意味やオプションを確認したい
- ログの調査やテスト実行に使うコマンドの候補が欲しい
- ターミナルで作業を続けながら Copilot を利用したい

### 頼み方の例

> Support Ticket Dashboard のテストのうち、優先度フィルターに関係するものだけを実行する方法を説明してください。実行前にコマンドの各部分の意味も示してください。

### 注意点

- 提案されたコマンドの意味と対象を理解してから実行します。
- ファイル削除、権限変更、外部への送信を行うコマンドは特に慎重に確認します。
- プロジェクトで定められた実行方法を優先します。

## GitHub Copilot Cloud Agent（発展）

GitHub Copilot Cloud Agent は、Issue などの作業内容を渡し、クラウド上の環境で非同期に作業させるための機能です。別の作業をしている間に変更案を作成してもらい、後から Pull Request の差分や結果を確認できます。

### 使う場面

- 要件と完了条件が明確な Issue の変更案を作ってほしい
- 独立した小さな修正を非同期で進めたい
- テストを含む定型的な変更を任せたい

### 頼み方の例

> Support Ticket Dashboard に優先度フィルターを追加してください。既存のステータスフィルターと併用できること、0 件表示を扱うこと、関連テストを追加することを完了条件とします。関係するファイル以外は変更しないでください。

### 注意点

- Issue に背景、対象範囲、受け入れ条件、非対象を具体的に書きます。
- 認証情報など、作業に不要な機密情報を渡してはいけません。
- 完了後は、Pull Request の差分、実行結果、意図しない変更がないかを人間が確認します。
- 要件が曖昧な作業や、途中で頻繁な判断が必要な作業には向かない場合があります。

## custom instructions / Agent Skills（発展）

custom instructions は、命名規則、テスト方針、変更時の注意など、繰り返し伝えたいチームのルールを Copilot に共有する仕組みです。Agent Skills は、特定の作業で使う手順や知識を再利用できる形で用意する仕組みです。

### 使う場面

- プロジェクト固有のコーディング規約を毎回守ってほしい
- テスト、レビュー、リリースなどの定型手順を共有したい
- チームで Copilot への依頼方法と結果の品質をそろえたい

### 頼み方の例

> Support Ticket Dashboard では、既存コンポーネントの命名規則に従い、機能変更には正常系と 0 件時のテストを追加し、無関係なリファクタリングを行わない、というルールを custom instructions に反映する案を作成してください。

### 注意点

- 指示は短く具体的にし、互いに矛盾しないよう管理します。
- 古くなったルールは更新し、現在のコードやチームの方針と一致させます。
- 指示があっても常に守られるとは限らないため、差分と結果を確認します。
- パスや適用範囲などの詳細は、利用する環境の公式ドキュメントで確認します。

## 迷ったときの選び方

1. **まだコードや原因が分からない**なら Ask Mode
2. **何をどう変更するか決めたい**なら Plan Mode
3. **方針が決まり、実際に変更したい**なら Agent Mode
4. **変更が終わり、抜け漏れを探したい**なら GitHub Copilot Code Review

CLI、Cloud Agent、custom instructions / Agent Skills は、基本の流れを理解した後に、作業場所やチームの進め方に合わせて利用する発展的な選択肢です。
